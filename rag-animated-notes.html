01

What RAG is — three words, three jobs

RAG is a technique that connects a Large Language Model to external knowledge at answer time. The model itself doesn't change — what changes is what it gets to read before it answers. Tap each letter.

The one-line memory hook

RAG = open-book exam. A plain LLM sits a closed-book exam from memory. RAG lets it open the book at the right page first. Fine-tuning, by contrast, rewrites what's in the student's head — a very different (and slower) operation, covered in section 12.

02

Why RAG exists — the four gaps in a bare LLM

An LLM's knowledge is frozen at training time and limited to what was public. Real work runs into four walls — RAG is the door through all of them.

Gap 1

Private data

Your company's plan documents, internal manuals and customer policies were never in the training data. The model literally has never seen them — so it guesses.

Gap 2

Outdated knowledge

Training ends at a cutoff date. Rules change, products change, circulars are issued after it. A bare model answers with last year's rule, confidently.

Gap 3

Cost of retraining

Teaching the model new facts by retraining or fine-tuning is slow and expensive — and you'd repeat it every time a document changes. Documents change daily.

Gap 4

No source, no trust

A bare model can't show its working. In enterprise use — insurance, banking, healthcare — an answer you can't trace to a document is an answer you can't use.

See the difference — same question, two systems

A question from real policy servicing. Switch between the two systems and compare what comes back.

03

Hallucination — the problem RAG is really fighting

A hallucination is a fluent, confident answer that is simply not true. Understanding why it happens explains why retrieval helps.

Cause 1

It predicts words, not facts

An LLM is trained to produce the most likely next token. When the true fact isn't in memory, the most likely-sounding sentence is still produced — likelihood is not truth.

Cause 2

Gaps get filled smoothly

Training rewards complete, helpful answers. The model rarely says “I don't know” — it bridges gaps with invented numbers, dates and clauses that fit the pattern.

Cause 3

No access to your truth

Your documents are the ground truth for your work, and the model can't see them. Every specific question about them is, to the model, a gap to fill.

How RAG reduces it — and the honest limit

RAG attacks Cause 3 directly and Cause 1 indirectly: the answer is generated conditioned on retrieved text, so the most likely continuation is now the documented one, and the system can cite its source. But RAG does not eliminate hallucination — if retrieval fetches the wrong chunk, or the model ignores the context, the answer can still be wrong. Grounding lowers the error rate; it is not a guarantee. Any honest RAG answer in an interview includes this caveat.

04

Two kinds of memory — parametric vs non-parametric

This is the concept slide of the whole carousel. RAG is best understood as a bridge between the two places knowledge can live.

Inside the model

Parametric memory

Knowledge stored in the model's weights (its parameters) during training. Language, reasoning patterns, general world knowledge.

  • Fixed at training time — a frozen snapshot
  • Updating it means retraining: slow, costly
  • Can't hold your private documents
  • Can't tell you where a fact came from
Outside the model

Non-parametric memory

Knowledge stored outside the model, in a searchable index — a vector database of your documents, built and owned by you.

  • Updated by re-indexing a document: minutes
  • Holds private, current, enterprise data
  • Every fact traceable to its source chunk
  • The model reads it fresh on every question
RAG connects the two

Parametric memory gives the model its skills — language, reasoning, summarising. Non-parametric memory gives it the facts for this question. RAG is the pipe between them: retrieve from the outside store, reason with the inside one. You keep each where it's cheapest to maintain.

05

The complete architecture — two phases

Every RAG system, from a weekend project to an enterprise deployment, has the same skeleton. Phase A runs once per document (offline). Phase B runs on every question (live). Press play and watch both.

Phase A

Indexing pipeline — done in advance

🗂️Data sourcesPDFs, Word docs, web pages, wikis, databases
📥Load documentsExtract clean text from each file format
✂️Chunk textSplit into small, searchable pieces
🔢Embed chunksTurn each chunk into a vector of numbers
🗄️Vector databaseStore vectors + text, indexed for fast search
Phase B

Query & generation pipeline — done per question

❓User queryThe question arrives
🔢Embed querySame embedding model turns it into a vector
🔍RetrieveFind the nearest chunk vectors
🏅RankOrder by relevance; keep the top-k
🧩Augment promptQuestion + top chunks become one prompt
✍️GenerateLLM answers from the context, with sources

Phase A happens once — after that, only Phase B runs, which is why answers take seconds, not hours.

06

Document ingestion & loading — garbage in, garbage out

Phase A starts with a messy real-world step: turning files people actually have — PDFs, scans, Word documents, web pages — into clean text a machine can chunk and embed.

Step 1

Load

A document loader per format reads the file: PDF text extraction, HTML parsing that strips navigation and boilerplate, Word/Excel readers, database connectors.

Step 2

Clean

Remove page headers, footers, page numbers and repeated disclaimers that would otherwise pollute every chunk and waste retrieval slots.

Step 3

Tag with metadata

Attach source file, section heading, page number and date to every chunk. Metadata is what later powers citations — and filters like “only search the 2026 circulars”.

The tester’s instinct applies here

Most RAG failures blamed on “the model” are actually ingestion failures: a scanned PDF whose text layer is garbage, a table flattened into nonsense, the wrong version of a document indexed. When a RAG answer is wrong, check the retrieved chunk first — if the chunk is wrong, the pipeline failed before the LLM ever got involved.

07

Chunking — why documents are cut into pieces

You can't embed a 300-page policy document as one vector, and you can't paste it all into a prompt. Chunking splits text into small pieces that are each about one thing — small enough to retrieve precisely, big enough to still make sense.

Too big

Giant chunks

One chunk covers five topics, so its vector is an average of everything and matches nothing well. Retrieved chunks also blow the context window.

Too small

Tiny chunks

A single sentence loses its surroundings — “the period is 5 years” is useless if the chunk doesn't say 5 years for what. Meaning needs context.

The fix

Overlap

Consecutive chunks share some text (e.g. 10–20%). A sentence cut at a boundary still appears whole in the neighbouring chunk, so nothing falls through the crack.

Chunking lab — try it on a real clause

Drag the sliders and watch the same policy paragraph get re-cut. Notice how overlap repeats the boundary text in two chunks.

Strategy 1

Fixed-size

Cut every N characters or tokens, blind to content. Simple and predictable — but can slice a sentence, or a clause, in half.

Strategy 2

Recursive / structural

Split on natural boundaries first — paragraphs, then sentences, then words — only going finer when a piece is still too big. The common default in frameworks like LangChain.

Strategy 3

Semantic

Embed sentences and cut where the meaning shifts. Best topic purity, but slower and more complex to build.

08

Embeddings — turning meaning into numbers

An embedding model converts a piece of text into a long list of numbers — a vector (often 384 to 1,536 numbers). The magic property: texts with similar meaning get vectors that point in similar directions, even if they share no words.

Why this matters more than keywords

Keyword search for “revival period” misses a chunk that says “a discontinued policy may be restored within five years” — no shared words, same meaning. Embedding search finds it, because restored and revival live close together in vector space. That is the entire reason RAG uses vectors instead of a plain text search.

Nearest neighbours

Tap any word in the map. Real embeddings have hundreds of dimensions; this is a 2-D sketch of the same idea — closeness = similarity of meaning.

Closest to policy:

    what an embedding actually looks like

    One rule that follows from this: the query and the documents must be embedded by the same model. Vectors from different models live in different spaces — comparing them is like comparing a temperature in Celsius with one in Fahrenheit without converting.

    09

    Vector similarity — how “close” is measured

    Retrieval needs a score for “how similar is this chunk's vector to the query's vector?” Three measures dominate. Drag the angle and watch the most important one change.

    0.91Cosine similarity — cos of the angle. 1 = same direction (same meaning), 0 = unrelated, −1 = opposite. The default for RAG.
    —Dot product — angle and length together. Faster to compute; equals cosine when vectors are normalised.
    —Euclidean distance — straight-line gap between the arrow tips. Smaller = closer. A distance, not a similarity.

    Cosine wins for text because it cares about direction (meaning), not length — a long chunk and a short chunk about revival should score as similar even though their vectors differ in magnitude.

    10

    Retrieval & ranking — picking the top-k

    The vector database scores every chunk against the query vector, sorts by similarity, and returns the best few — the top-k. Only those chunks go into the prompt. Move k and see the trade-off.

    Query“What is the revival period for a lapsed policy, and what must be paid?”

    k too small

    Missing evidence

    k = 1 bets everything on a single chunk. If the answer needs two clauses — the period and the charges — one chunk can't hold both, and the model fills the gap by guessing.

    k too big

    Noise and cost

    k = 20 drags in weakly-related chunks. They dilute the prompt, cost more tokens, and can actively mislead the model — a chunk about a different plan's period looks authoritative.

    Re-ranking — the quality upgrade

    Many production systems add a second pass: retrieve a generous top-20 by fast vector search, then run a slower, smarter re-ranker model over just those 20 to pick the true top-3 or 4. Cheap breadth first, expensive precision second — the same reason a search engine doesn't deep-read the whole web for your query.

    11

    Prompt augmentation — assembling the final prompt

    Retrieval's output becomes the prompt's input. This is the exact moment “augmented” happens — and the instruction line at the top is what keeps the model honest.

    the prompt the LLM actually receives
    SYSTEM: Answer the question using ONLY the context below. If the context does not contain the answer, say "I don't have that in the documents" — do not guess. CONTEXT: [1] "A lapsed policy may be revived within 5 years from the date of the first unpaid premium…" (Policy_Conditions.pdf, Clause 7) [2] "Revival requires payment of all arrears of premium with interest, plus a revival fee…" (Policy_Conditions.pdf, Clause 7) QUESTION: What is the revival period for a lapsed policy, and what must be paid to revive it?
    Part 1

    The instruction

    “Use only the context; admit when it's missing.” This one line is the main guardrail against the model drifting back to its parametric memory.

    Part 2

    The context

    The top-k chunks, pasted verbatim, with source labels so the model can cite them — and so a human can verify the answer afterwards.

    Part 3

    The question

    The user's original words, unchanged. The model now answers an open-book question: everything it needs is on the page in front of it.

    12

    RAG vs fine-tuning vs retraining

    The comparison the carousel builds towards. All three “teach” an AI system something — but they change different things, at wildly different costs. The deciding question: are you changing facts, behaviour, or the brain itself?

    QuestionRAGFine-tuningRetraining
    Changes model weights?No — model untouchedYes — adjusts weights on your examplesYes — builds weights from scratch
    Best forNew or changing facts: documents, policies, prices, manualsNew behaviour: tone, format, a specialised style of answeringA fundamentally new model or capability
    Update speedMinutes — re-index the changed documentHours to days — new training run + evaluationWeeks to months, very large compute
    CostLow — storage + embedding callsModerate — GPU time and curated example dataVery high — the full training pipeline
    Private dataYes — stays in your own vector storeRisky — facts get baked into weights, hard to removeNot the tool for this
    CitationsYes — every answer traces to a chunkNo — knowledge is blended into weightsNo
    Can it un-know a fact?Yes — delete the chunkHard — would need retrainingNo
    Why RAG avoids repeated retraining — the core argument

    Facts change constantly; retraining to chase them is like reprinting an encyclopedia every time a phone number changes. RAG keeps facts in a database you control — update the document, re-embed it, and the very next answer uses the new fact. And the two combine: many real systems fine-tune for behaviour and use RAG for facts. They solve different problems; “RAG or fine-tuning” is usually the wrong framing.

    13

    Limits & failure modes — what to check when RAG goes wrong

    A RAG pipeline has more moving parts than a bare LLM call, and each part can fail in its own way. This is also, not coincidentally, a test plan.

    Failure 1

    Retrieval misses

    The right chunk exists but scores below the top-k — bad chunking, a poorly-worded query, or the wrong embedding model. The LLM then answers from the wrong evidence, fluently.

    Failure 2

    Stale index

    The document was updated but never re-indexed. RAG is only as current as its last indexing run — “the PDF changed on Monday” means nothing until Phase A runs again.

    Failure 3

    Model ignores context

    Given correct chunks, the model still answers from parametric memory — especially when its training “knowledge” conflicts with the document. Strong instruction lines and evaluation are the mitigations.

    Failure 4

    Chunk-boundary answers

    The answer is split across two chunks and neither is retrieved whole. Overlap exists precisely to fight this — which is why the chunking lab in section 07 matters.

    Testing a RAG system — the SDET angle

    If you're ever asked how you'd test one, the pipeline gives you the checklist — each stage is testable separately:

    • Retrieval tests: for a set of known questions, is the correct chunk inside the top-k? (Recall@k.)
    • Groundedness tests: does every claim in the answer appear in the retrieved context — or did the model add facts?
    • Refusal tests: ask something the documents don't cover. The correct behaviour is “not in the documents”, not an invention.
    • Freshness tests: update a document, re-index, and verify the new fact is what comes back.
