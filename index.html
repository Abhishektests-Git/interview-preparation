It cannot skip a station, and if it fails the test station, it falls off the belt and never reaches Production. Press play and watch one build make the full journey.

How Jenkins works — the machine that runs the belt

Jenkins is the automation server behind the animation above. It watches for new code, then runs the same fixed stations every single time — nobody has to start it by hand.

🖥️

Jenkins Server the boss · also called the Controller

The machine that watches Git for new code and runs the belt. It decides what runs, in what order, and records the result of every run.

📜

Job / Pipeline the recipe

The fixed list of stages — Build → Test → Deploy — written once and run the same way every time. One job = one belt.

📦

Stages the stations

Each station on the belt is a stage. Jenkins shows every stage as a box that turns green when it passes, red when it fails — a red stage stops the whole run.

🦾

Agent / Node the worker

The machine that actually does the work the boss assigns: compiling the code and running your Selenium + TestNG tests. A busy team can have many agents.

⏰

Triggers what starts the belt

Three ways a run starts: a Git webhook the moment code is pushed, a schedule (for example a nightly regression run), or a manual click on “Build Now”.

📊

Reports & Result the verdict

After testing, Jenkins publishes the result and the report — in your project, the TestNG / Extent Report. Green build = SUCCESS, red build = FAILURE, and a failed build is never deployed.

What you learnt — the whole session in six lines

If you remember only this page's recap before an interview, you have the full picture.

  • Pipeline = a fixed line of stations. Every change travels Code → Build → Test → Deploy, in order, with no skipping.
  • Testing happens in the QA environment, before Production. Code is deployed first to a test server that copies the real system — breaking things there is safe.
  • Sanity first, then change testing + regression. If the app doesn't even open or login fails, stop immediately — there is no point running the full suite.
  • A failed test stops the belt. The build loops back to the developer, gets fixed, and re-enters from the very start as a new build — it never moves forward.
  • The same tested build is promoted. The exact build that passed in QA is the one that goes to Staging and then Production — it is not rebuilt.
  • Jenkins runs the whole belt automatically. A Git push wakes it up, its job runs every stage on a worker agent, and it publishes the result and report at the end.

Say it in an interview

Your project, in one answer

“In our project, whenever code was pushed to Git, a webhook triggered Jenkins. Jenkins built the code with Maven and deployed the same build to the QA environment. Sanity ran first, then our Selenium–TestNG suites — change testing and regression. If any test failed, Jenkins marked the build FAILURE, a defect was raised, and the build never moved ahead; the fix came back as a new build and was retested with regression. Only a fully green build was promoted towards production, and Jenkins published the Extent Report for every run.”
