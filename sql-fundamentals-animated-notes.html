01

SELECT * vs naming your columns

SELECT * means "give me every column in the table" — including the ones you don't need. Naming columns means asking for exactly what your code uses, nothing more.

SELECT * 😮‍💨

Everything comes over the wire:

policy_noholder_namepremium sum_assuredstatusmaturity_date remarks (long text)doc_blob (huge file)

Name the columns 🎯

Only what the report needs:

policy_noholder_namepremium

Two ways to ask the same table for data. Press Play to compare them.

-- ❌ lazy and risky SELECT * FROM policies; -- ✅ clear and safe SELECT policy_no, holder_name, premium FROM policies;
  • Extra weight: SELECT * pulls columns nobody uses — slow queries, wasted memory.
  • Breaks silently: someone adds, drops or reorders a column and your code misbehaves or crashes, because it was secretly depending on "all of them, in that order".
  • Hides intent: a reader can't tell which columns the code actually needs.
Remember: SELECT * is a shortcut that borrows trouble — always name the columns you need.

The INT family — small, medium, large, huge

Whole numbers come in four sizes. A bigger size wastes space on every row; a smaller size overflows when the number outgrows it. So you pick the smallest size that safely fits the values you'll ever store.

TINYINTmax 255
SMALLINTmax 32,767
INTmax ≈ 2.1 billion
BIGINTmax ≈ 9.2 quintillion

Same family, four sizes. Press Play to watch them grow.

-- age will never pass 120 → small is fine age SMALLINT, -- policy numbers keep growing for decades → room to grow policy_no INT
Remember: smallest type that safely fits — an age doesn't need BIGINT, and a forever-growing ID must never sit in SMALLINT.
04

CHAR vs VARCHAR — fixed boxes vs flexible boxes

Both store text. The difference is storage: CHAR(10) always reserves 10 characters and pads the empty space; VARCHAR(10) reserves only what the text actually uses (up to 10).

CHAR(10) — fixed

Ram ···· ···

"Ram" + 7 spaces of padding = always 10

VARCHAR(10) — flexible

Ram

"Ram" = just 3 — grows only when the text does

Same word, two storage styles. Press Play to see the padding.

  • Use CHAR when every value is truly the same length — like a 2-letter state code (BR DL).
  • Use VARCHAR for names and most text — lengths vary, so don't pay for empty boxes.
📄 Really long text — policy remarks, claim notes, full addresses? Use TEXT / VARCHAR(MAX), made for long, free-form writing.
Remember: CHAR = fixed rent for the whole flat; VARCHAR = pay only for the rooms you use.
05

DECIMAL vs FLOAT — why money is never a float

FLOAT stores numbers approximately — close, but not exact. DECIMAL(p, s) stores exact digits: p = total digits, s = digits after the decimal point. Watch what that tiny difference does to simple addition.

FLOAT — approximate 😬

0.1 + 0.2 =0.30000000000000004

Close… but not equal. A paisa here, a paisa there.

DECIMAL — exact ✅

12500.50 + 999.50 =13500.00

Premium maths lands on the exact rupee and paisa.

One addition, two outcomes. Press Play to see which type drifts.

-- money columns: always DECIMAL premium DECIMAL(10,2), -- 8 digits + 2 paise digits sum_assured DECIMAL(12,2), claim_amount DECIMAL(12,2)
  • Money = DECIMAL, always. Premiums, sum assured, claim amounts — one paisa of drift fails a reconciliation.
  • FLOAT is fine for scientific measurements — temperature, weights — where a tiny error changes nothing.
Remember: if a human will ever count it or audit it, it's DECIMAL. FLOAT is for measurements, not money.

BOOLEAN / BIT — the yes-no switch

Some questions have only two answers: is this policy active? Was the premium paid? Databases store that as a BIT — 1 or 0, shown to you as TRUE / FALSE.

policy_active = TRUE → stored as 1

policy_active = FALSE → stored as 0

One column, two states. Press Play to flip the switch both ways.

SELECT policy_no, holder_name FROM policies WHERE policy_active = 1; -- only live policies
Remember: a yes/no fact deserves a BOOLEAN/BIT — never a text column full of 'Yes', 'yes', 'Y' and surprises.

NULL means "unknown / not there yet". It is not zero, and it is not empty text. A running policy has no maturity payout date yet — so maturity_date is NULL. That one idea explains half of all "my query missed rows" bugs.

09

COALESCE & NULLIF — the NULL-handling tools

Two small functions fix most NULL pain. COALESCE swaps a NULL for a backup value. NULLIF does the reverse — it turns a dangerous value into NULL, on purpose.

COALESCE — NULL becomes a backup

NULL→0
SELECT premium - COALESCE(premium_discount, 0) FROM policies;

NULLIF — safe division

100 / 0💥 error
100 / NULLIF(0,0)NULL — no crash

One function removes NULLs, the other creates them — both save your query.

-- average premium per policy, safe even when count could be 0 SELECT total_premium / NULLIF(policy_count, 0) AS avg_premium FROM branch_totals;
Remember: COALESCE fills NULL holes with a backup; NULLIF turns a 0 denominator into NULL so division fails soft instead of crashing.
10

Casting — changing a value's type

Sometimes a number must become text, or text must become a number. That conversion is called casting, and it happens two ways: quietly by the database, or openly by you.

Implicit — the database guesses 😟

WHERE policy_no = '1024' -- INT vs text: silent conversion happens

Risky: hidden conversions, hidden errors, slow queries.

Explicit — you say it out loud ✅

SELECT CAST(policy_no AS VARCHAR(10)), CAST('2026-11-26' AS DATE) FROM policies;

Clear: the conversion is visible to every reader.

Same conversion, two styles — one hidden, one honest.

Remember: convert explicitly with CAST — if a conversion matters, it should be visible in the query, not guessed by the database.

Collation, case & Unicode

A collation is the rulebook a column uses to compare and sort text: is 'A' before 'a'? Is 'Ram' the same as 'RAM'? The rulebook decides — and different databases pick different defaults.

Case-insensitive rulebook

'Ram' = 'RAM'TRUE

Case-sensitive rulebook

'Ram' = 'RAM'FALSE
🌍 NVARCHAR stores names like राम कुमार or Zoë 🎂 exactly as written. VARCHAR can garble or reject characters outside plain English.

Same comparison, two rulebooks, two answers — plus the Unicode twist.

Remember: collation is the text rulebook — and if names can arrive in any language, store them as NVARCHAR.

LIKE — searching text by pattern

= needs an exact match. LIKE matches a pattern, using two wildcards: % = any run of characters (even none), and _ = exactly one character.

Pattern: holder_name LIKE 'Ra%'

Ram ✔Rakesh ✔ Ravi ✔Sunita ✘

Pattern: holder_name LIKE 'R_m'

Ram ✔Raam ✘ — one character too many
LIKE '50\%' ESCAPE '\' → finds a real % sign ILIKE 'ra%' → case-insensitive LIKE (PostgreSQL) elsewhere: LOWER(name) LIKE 'ra%'

Two wildcards, matched live against real holder names.

SELECT policy_no, holder_name FROM policies WHERE holder_name LIKE 'Ra%'; -- every holder whose name starts with Ra
Remember: % stretches to any length, _ is exactly one character — 'Ra%' finds a crowd, 'R_m' finds a shape.

ORDER BY — where do the NULLs land?

Sorting sounds simple until a NULL shows up. The awkward truth: databases disagree on where NULLs belong in a sorted list — so the same query can show different orders on different systems.

Outcome A — NULLs last

premium 300premium 500premium 1200premium NULL

Outcome B — NULLs first

premium NULLpremium 300premium 500premium 1200
ORDER BY premium ASC NULLS LAST; -- standard SQL, PostgreSQL, Oracle

MySQL and SQL Server don't support NULLS LAST — there, sort by a yes/no first: ORDER BY (premium IS NULL), premium pushes NULLs to the end the portable way.

One sort, two possible outcomes — press Play, then see the fix.

Remember: never leave NULL position to the database's mood — pin it with NULLS FIRST / NULLS LAST where supported, or the (col IS NULL) trick where it isn't.

15

Say it in an interview

The five questions from this part that interviewers ask most — with short, confident answers in plain words.

Q. Why should we not use SELECT *?

"Three reasons. It fetches columns nobody needs, which wastes time and memory. It makes the code fragile — if someone adds, drops or reorders a column, the application can break or read the wrong data. And it hides intent — naming columns shows exactly what the query depends on."

Q. CHAR vs VARCHAR — what's the difference?

"CHAR is fixed length — CHAR(10) always stores 10 characters and pads shorter values with spaces, so it suits fixed-size codes. VARCHAR is variable length — it stores only the characters actually used, up to the limit, so it's the right choice for names and most text."

Q. Why DECIMAL for money, not FLOAT?

"FLOAT stores values approximately — 0.1 + 0.2 can come out as 0.30000000000000004. In money that drift breaks totals and reconciliations. DECIMAL stores exact digits, so premiums and claim amounts always add up to the paisa. FLOAT is fine for scientific measurements where a tiny error doesn't matter."

Q. What is NULL? Why doesn't = NULL work?

"NULL means unknown or missing — it's not zero and not an empty string. Because it's unknown, any comparison with NULL gives UNKNOWN, never TRUE — even NULL = NULL. WHERE only keeps TRUE rows, so = NULL matches nothing. The correct test is IS NULL or IS NOT NULL. It's also why WHERE status <> 'Closed' silently drops rows whose status is NULL."

Q. How do you avoid divide-by-zero in SQL?

"Wrap the denominator in NULLIF: total / NULLIF(count, 0). If count is 0, NULLIF returns NULL, and dividing by NULL gives NULL instead of an error — the query completes, and I can handle the NULL afterwards, for example with COALESCE."

Remember: answer with the rule, one reason, and one example from your own tables — that shape wins every one of these.
