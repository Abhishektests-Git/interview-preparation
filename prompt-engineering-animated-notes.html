01

The basics: AI, GenAI, and the LLM

Prompt engineering only makes sense once you know what is on the other side of the text box.

AI

Artificial Intelligence

The broad field: systems that perform tasks we associate with human intelligence — recognising, predicting, deciding. Spam filters and recommendation engines are AI, but they don’t create anything new.

GenAI

Generative AI

The subset that generates new content — text, code, images, audio — instead of just classifying what exists. ChatGPT, image generators and code assistants live here.

LLM

Large Language Model

The engine underneath text GenAI. Trained on enormous amounts of text, it works by predicting the most probable next token, over and over. It doesn’t “know” facts like a database — it models patterns in language.

Why this matters for prompting

Because the model predicts likely text rather than looking up truth, the wording of your prompt is the strongest lever you have. Give it a vague pattern, you get the average of everything it has seen. Give it a precise role, context and format, and you steer the prediction toward exactly the corner of its training you want.

02

Tokens: the model’s alphabet

LLMs don’t read words — they read tokens: chunks of roughly ¾ of a word in English. Context windows, cost and limits are all counted in tokens. Try the simplified tokeniser below (real tokenisers use learned sub-word merges, so counts differ slightly).

Context window

The maximum tokens the model can “see” at once — your prompt plus its reply. Anything outside the window is forgotten, which is why long chats drift and why pasting the right context matters more than chatting longer.

Rule of thumb

100 tokens ≈ 75 English words. Code, URLs and non-English text usually cost more tokens per word — one reason a Hindi sentence can use more of the window than the same sentence in English.

04

Basic techniques

The everyday toolkit. “Shot” means an example included in the prompt — zero-shot is asking cold, few-shot is showing the pattern first.

Zero-shot — ask directly, no examples

Works when the task is common and well-represented in training. Fastest to write; quality depends entirely on how clearly the task is stated.

Classify the sentiment of this review as Positive, Negative or Neutral:
"The delivery was late, but the product quality is excellent."

Best for: summaries, translations, simple classification, definitions.

One-shot — show one example

A single example pins down the format far better than describing it. Use when the output shape matters more than the content.

Convert to a formal email line:
Casual: "hey, can't make it today"
Formal: "Hello, I will be unable to attend today."

Casual: "send me the file asap"
Formal:

Best for: tone conversion, fixed reply formats, naming conventions.

Few-shot — show the pattern 2–5 times

Multiple examples teach edge cases and consistency. Keep examples short, varied and in the exact format you want back.

Bug title → Severity
"App crashes on login with valid credentials" → Critical
"Typo in footer copyright year" → Low
"Payment succeeds but confirmation email missing" → High
"Search results show duplicate policies" →

Best for: classification with your own labels, data extraction, consistent test-case formats.

Instruction, question & contextual prompting

Instruction: command form — “Summarise…”, “List…”. Question: ask as a question when you want reasoning or explanation. Contextual: attach the situation so the answer fits it, not the generic case.

Context: I am preparing for an SDET interview tomorrow and know
Java and Selenium but not microservices.
Question: Explain waits in Selenium in 5 bullet points, at the
depth an interviewer expects, and flag the one follow-up question
they usually ask next.

Best for: study help, interview prep, anything where “for whom” changes the answer.

Iterative prompting — refine in rounds

Treat the first answer as a draft, not a failure. Each follow-up narrows one thing: scope, depth, format, tone, audience.

Round 1: "Explain recursion."
Round 2: "Now explain it with a Java example I can run."
Round 3: "Remove the theory. Give me only the code and a
          line-by-line dry run for factorial(4)."

Best for: learning, writing, debugging — anywhere the target sharpens as you see drafts.

05

Advanced techniques

For problems where one straight-line answer isn’t reliable. Watch chain-of-thought work through a problem step by step:

Chain-of-Thought (CoT) — “think step by step”

Prompt: A test suite has 240 cases. 15% are flaky. Of the flaky ones, ⅓ fail only on Mondays. How many cases fail only on Mondays? — press play and watch the reasoning chain.

1

Find the flaky cases: 15% of 240 = 0.15 × 240 = 36 flaky cases.

2

Take one third of those: 36 ÷ 3 = 12 cases.

3

Answer: 12 cases fail only on Mondays. Each step is checkable — that’s the point of CoT.

Decomposition

Break the problem down

Split a big task into sub-tasks and prompt for each in sequence: outline → sections → draft → polish. The model does each smaller job better than the whole job at once, and you can correct course between steps.

Self-consistency

Ask several ways, take the consensus

Generate multiple reasoning paths (or re-ask in fresh chats) and trust the answer most paths agree on. Disagreement is a signal the question is ambiguous or the model is guessing.

ReAct

Reason + Act

The pattern behind AI agents: the model reasons, takes an action (search, run code, call a tool), observes the result, then reasons again. Thought → Action → Observation, in a loop until done.

Reflection / self-critique

Make it review its own work

“Review your answer above. List any errors, unsupported claims or missing cases, then give a corrected version.” Models catch a surprising amount of their own sloppiness when explicitly asked to audit it.

Role / persona

Cast the model before you brief it

“You are a strict code reviewer at a bank” produces different — usually better-calibrated — output than the same question asked cold. The persona sets vocabulary, standards and what the model treats as important. Combine it with a task and constraints (see the Builder in §3) for the strongest everyday prompt.

06

Context engineering & RAG grounding

Modern prompting is less about one clever sentence and more about what you put in the window: instructions, examples, documents, conversation history. Retrieval-Augmented Generation (RAG) automates the document part.

Your question“What is the revival rule?”
→
RetrieveSearch your documents for relevant chunks
→
GroundChunks pasted into the prompt as context
→
GenerateModel answers from the chunks, not memory
→
Answer + sourcesTraceable back to the document

Grounding rules that work

  • “Answer only from the context below. If it isn’t there, say ‘Not in the provided documents’.”
  • Ask for a quote or section reference with each claim.
  • Put the most important context where the model attends best — start or end, not buried mid-prompt.

Why it matters

Grounding is the main defence against hallucination — fluent, confident, invented answers. A model answering from supplied text can be checked; a model answering from “memory” of its training cannot. When facts matter, supply the facts.

07

Structured output prompting

When the answer feeds another tool — a script, a spreadsheet, an API test — prose is a liability. Ask for a schema, show one example, and validate what comes back.

The prompt

Extract the test data as JSON matching this schema.
Output ONLY valid JSON, no commentary.

Schema:
{
  "policyNumber": string,
  "age": number,
  "sumAssured": number,
  "premium": number
}

Text: "Policy POL-88412, Mr Verma, age 42,
sum assured 500000, annual premium 38500."

The output — then validate it

{
  "policyNumber": "POL-88412",
  "age": 42,
  "sumAssured": 500000,
  "premium": 38500
}
  • Does it parse as JSON? (Run it through a validator.)
  • Are all required fields present, with the right types?
  • Do the values match the source text — not just the shape?

Tester’s note: structured output is where prompt engineering meets API testing. The same discipline as validating a response body against a schema in RestAssured — expected shape first, then values, then edge cases (missing field, wrong type, extra field).

08

Weak prompt vs strong prompt

Same goal, same model. The only difference is the prompt. Toggle between them:

"Write test cases for login."

You’ll get a generic list — happy path, wrong password, maybe SQL injection if you’re lucky. No format, no coverage target, no connection to your application.

Role: missingContext: missingFormat: missingConstraints: missing
"You are a QA engineer on a life-insurance policy admin
system. Write test cases for the login page in a markdown
table with columns: ID, Scenario, Steps, Expected Result.
Cover: valid login, locked account after 3 failed attempts,
session timeout, and password reset. Negative cases first.
Maximum 10 cases."

Every block from §3 is present — so the output arrives in the shape you need, at the coverage you asked for, ready to paste into your test management tool.

09

Prompting for real work

Four domains from the carousel, each with the pattern that makes it reliable.

Coding

Specify language, version, and standards

“In Java 17…” beats hoping. Ask for edge cases and complexity, and treat generated code like a junior’s PR: compile it, test it, review security-sensitive parts (inputs, SQL, auth) yourself. Reusable workflow: explain → generate → test → refactor, one prompt each.

"In Java 17, write a method to find the second
largest number in an int array. Handle duplicates
and arrays shorter than 2. Then give 5 test inputs
with expected outputs."
Content creation

Brief first, draft second

Give audience, purpose, tone, length and structure before asking for the draft — the same brief you’d give a human writer. Then iterate on sections, not the whole piece.

"Audience: first-time home buyers in India.
Tone: reassuring, no jargon. Write a 120-word
intro for a guide on home-loan documents,
ending with one question that invites comments."
Education & learning

Ask it to teach, not to hand over

“Explain, then quiz me” builds understanding; “give me the answer” builds nothing — and submitting AI output as your own work breaks academic integrity rules in most institutions. Use it as a tutor: examples, hints, practice questions, feedback on your attempt.

"Teach me SQL JOINs using a POLICIES and
CUSTOMERS table. Explain one join at a time,
then ask me one practice question and wait
for my answer before continuing."
Data science & analysis

Demand defensible analysis

Ask for the method before the conclusion: which columns, which aggregation, what was excluded and why. And keep the classic trap in view — correlation is not causation; a pattern in data is a question, not a proof.

"Analyse this defect data: count defects by
module and severity, show the calculation for
each number, and list what this data cannot
tell us. Do not invent missing values."
10

Multimodal prompting & responsible use

Multimodal

Prompting with more than text

  • Image input: attach the image, then say what to look at — “Read the error message in this screenshot and suggest the likely cause.”
  • Image generation: subject + style + composition + lighting. You are art-directing, not describing a photo that exists.
  • Audio/docs: ask for transcript first, summary second — verify against the source before trusting either.
  • Keep the two jobs separate in your head: prompting a model to analyse media vs to generate media need different instructions.
Responsible AI

Rules that keep you safe

  • Verify facts. Fluency is not accuracy — check names, dates, numbers and quotes against a real source.
  • Protect data. Don’t paste passwords, personal data, or confidential company code into public tools.
  • Own the output. If your name is on it, you are responsible for it — errors included.
  • Disclose AI assistance where your employer, exam or publisher requires it.

Q1. What is prompt engineering?

The practice of designing inputs to an LLM — role, task, context, examples, format and constraints — so its output is accurate, in the right shape, and repeatable. It matters because the model predicts text from patterns: the prompt is how you steer which pattern it follows.

Q2. Zero-shot vs few-shot — when do you use each?

Zero-shot for common tasks where the model already knows the pattern (summarise, translate). Few-shot when the output format or labels are yours — classification schemes, test-case formats, extraction — because examples pin the pattern down better than descriptions do.

Q3. How do you reduce hallucinations?

Ground the model: supply the source text and instruct it to answer only from it, ask for quotes or references per claim, use structured output so answers are checkable, and verify anything factual against a real source. Lower freedom + supplied facts = fewer inventions.

Q4. What is chain-of-thought prompting?

Asking the model to reason step by step before giving a final answer. Multi-step problems (maths, logic, debugging) get more accurate because each intermediate step constrains the next — and the steps are visible, so you can spot where reasoning went wrong.

Q5. How would a tester use prompt engineering at work?

Generating test-case drafts in a fixed format from a requirement, producing test data, explaining error logs, drafting defect reports, and creating SQL or automation snippets — always with the tester reviewing, correcting and owning the final artefact, exactly like reviewing a junior’s work.

Q6. What is RAG, in one minute?

Retrieval-Augmented Generation: instead of relying on what the model memorised in training, the system first retrieves relevant chunks from your documents, puts them in the prompt as context, and the model answers from those chunks. It makes answers current, source-based and checkable — the standard pattern for chatbots over company documents.
